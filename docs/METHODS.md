# zna: Methods

This document describes the algorithms zna implements and the reasoning behind the constants they use: how paired reads are merged, how that scan is made bit-reproducible, what per-record fragment geometry and provenance the format carries, and how records are packed, normalized, labeled and shuffled. It is written for two readers — a bioinformatician deciding whether the output can be trusted, and a maintainer who needs to know why the merge floor is `log₂(N/α)` bits for each pair rather than a tuned constant. It is not a user guide (the README covers the CLI and the API), not a wire-format specification beyond what the algorithms depend on, and not a record of how the code arrived here: no history, no status, no roadmap. Where prose and code disagree the code is the authority, and load-bearing claims below carry file and line citations so each can be checked against it. **Line numbers drift** — an 0.5.1 audit found roughly half the citations off by tens to hundreds of lines after two releases — so resolve each by the named symbol, not the number; the file half of every citation was verified current at 0.5.1, and §1–§3 were rewritten against the 0.6 tree, citing symbols rather than lines.

**Measurements.** Merge numbers come from two ground-truth measurements, and each passage says which.

- **The 0.5.x benchmark** (`docs/MERGE_BENCHMARK_RESULTS.md` §1–§8, run at `710957d`): 1,000,000 read pairs simulated from hg38 at 2×150, fragment lengths uniform on [60, 450], 0.2% per-base sequencing error, a position-degrading NovaSeq quality profile, scored against fastp. Its numbers describe 0.5.x's decision (fixed thresholds, a trim band). They are quoted where the property measured is unchanged in 0.6 — the score, the merge construction, the consensus, the 5' invariant — and labelled 0.5.x where it is not.
- **The 0.6 qualification** (`docs/MERGE_BENCHMARK_RESULTS.md` §9, 2026-09-26): the same hg38 recipe regenerated byte-identically, plus khorana's chr22 simulation (error-free, reads clipped to the molecule) and three transcriptome sets (clean; 0.2% error with adapters; the noisy set passed through fastp), 4.11M pairs in all, every pair classified against truth under both 0.5.3 and 0.6 at the defaults (`α` 10⁻⁶, `--error-rate` 0.01).

The hg38 counts that recur below, and how they reconcile. Under 0.6, of 1,000,000 input pairs **580,144** merged and 419,856 were kept whole; 495 of the merges produced a record below `--min-read-length 40` and were dropped entirely — every one of them a wrong merge — so **579,649** merged records and **839,712** mate records are emitted, **1,419,361** in total. (0.5.x on the original run: 582,866 merged, 504 dropped, 1,416,630 records.) Kernel timings and compression ratios come from separate measurements, described where they appear.

## 1. The overlap score and the merge decision

### 1.1 One unknown

Write R1 and revcomp(R2) on a single axis. The only quantity that is not observed is the fragment length `L`, and it is equivalent to the signed offset `s` of revcomp(R2) relative to R1:

```
s = L - len2
```

uniformly, for every geometry: `s > 0` is a normal partial overlap, `s = 0` is exact full overlap, and `s < 0` is read-through, where each mate runs past the far end of the fragment into adapter. There is one axis and one scan, over `s ∈ [-(len2-1), len1-1]` — or a suffix of it when the input is declared adapter-trimmed (§1.7); each `s` fixes the compared region as the intersection of the two reads, so mates of unequal length (after quality trimming) need no special case.

That is the whole geometry. Everything downstream is a function of `s` alone — the merged record is the span `[0, L)` with `L = s + len2`, which mate supplies which base follows from where `len1` falls inside that span, and the redundant overlap is `len1 + len2 - L`. No per-direction case analysis is needed anywhere, and none is used.

A pair has exactly two outcomes: **merged** into one full-fragment record, or **kept** as its two input mates. There is no third (§1.9).

### 1.2 The score

For a candidate `s` the scan sees `n` aligned base comparisons, `m` of them matching and `d = n - m` mismatching, and weighs two hypotheses:

- **H₁, real overlap.** A disagreement is a sequencing error, with probability `e` — `--error-rate`, default 0.01. It is the probability that two aligned *real* overlap bases disagree, roughly twice the per-base error rate, since either read can be wrong. §1.4 gives its two roles and why it is a parameter rather than an estimate.
- **H₀, chance alignment.** Unrelated bases agree one time in four (`P_NULL = 0.25`).

The score is the log-likelihood ratio in bits:

```
score(s) = m · log₂((1-e)/0.25)  -  d · log₂(0.75/e)
         = m · match_w  -  d · mismatch_w
```

At `e = 0.01`, `match_w = 1.9855` and `mismatch_w = 6.2288` bits (`weights_q`, `src/zna/merge/params.py`). Neither is a tuning knob: both fall out of `e`.

A matching base is worth just under `log₂ 4 = 2` bits, the information in two reads agreeing on one of four bases, and the shortfall is load-bearing rather than cosmetic: it is what puts the shortest mergeable clean overlap at `ceil(T / 1.9855)` = 14 bases at 2×50 and 2×100 and 15 at 2×150 and 2×300 (§1.3), pinned by `test_the_shortest_mergeable_clean_overlap` in `tests/test_merge.py`.

Comparison is raw byte equality on upper-cased sequence: `N` agrees with `N`, and IUPAC codes agree with themselves. There is no separate ambiguity case in the kernel, so no fast path can disagree with the reference implementation on any input; §2.4 explains why byte comparison is the specification rather than an approximation of it. Where an `N` is *uninformative* rather than a disagreement — in the plausibility gate and the run's disagreement statistic — it is discounted there, never in the score (§1.5).

The score is computed in integers, never in floating point: `int64` fixed point at 2⁻²⁴ bits per unit, with both weights derived once in Python with correctly rounded `decimal` arithmetic and crossed into C++ as integers. No float takes part in a comparison, a bail bound, the argmax or the gate, so a given FASTQ produces the same output on every compiler, optimization level and platform — this is training data, and the corpus must not depend on the machine. §2.1 gives the arithmetic and the enumeration that checks quantization against the per-pair floor.

**Quality scores do not enter the score.** The scan takes two scalar integer weights derived from a single `e` (`weights_q`; scan signature `scan_eligible` in `merge_core.hpp`) against a fixed null, `P_NULL = 0.25` (`params.py`). There is no per-position (Q1, Q2) score table and no composition-aware null. Quality is used only in the consensus (§1.10), through a precomputed posterior table — which is what removes the need for quality cutoffs anywhere in the decision. One consequence of the fixed null is worth naming: there is no low-complexity correction, so a 20-base polyA scores 39.7 bits clean and clears the floor only where it is the whole overlap; `test_polya_does_not_merge` pins that 0 of 200 pairs with polyA tails on both mates merge.

### 1.3 The merge floor, derived per pair

Under H₀ any likelihood ratio has `E[LR] = 1`, so `P(score ≥ T) ≤ 2⁻ᵀ` per shift. A pair has `N = len1 + len2 − 1` candidate shifts, and a union bound over them caps a chance merge of unrelated sequence at `N · 2⁻ᵀ` per pair. Setting that to the one tolerance `α` (`--alpha`, default 10⁻⁶) gives the floor:

```
T(N) = log₂(N / α)          N = len1 + len2 − 1
```

`T` is not chosen; it is read off `α` for each pair's own geometry (`threshold_q`, `t_table` in `params.py`):

| reads | N | T (bits) | shortest clean overlap |
|---|---:|---:|---:|
| 2×50 | 99 | 26.56 | 14 |
| 2×100 | 199 | 27.57 | 14 |
| 2×150 | 299 | 28.16 | 15 |
| 2×300 | 599 | 29.16 | 15 |

0.5.x used a fixed 28 bits, which is this formula at 2×150 — so the default `α` keeps the operating point that 0.5.x's threshold sweep chose (below) and makes it correct at every other read length. Evidence accumulates linearly while the false-positive rate falls exponentially, so being conservative is cheap: each factor of 10 in `α` moves `T` by 3.3 bits, about 1.7 matching bases.

Concretely, the matches required to clear the floor at 2×150 (pinned by `TestDetection` so the arithmetic cannot drift):

| mismatches in the overlap | matches needed at T = 28.16 |
|---|---|
| 0 | 15 |
| 1 | 18 |
| 2 | 21 |
| 3 | 24 |

Each mismatch costs `mismatch_w / match_w = 3.14` matching bases.

The resulting sensitivity cliff is exactly where the arithmetic puts it. On the 0.5.x benchmark (floor 28 bits, and the same 15/18/21/24 lattice as above), merges go from ~1% below 15 bases of true overlap to 92.55% in the 15–19 bin and 99.76% at 20–29. The shortfall in the first bin is arithmetic rather than slack: a 15-base overlap scores 29.8 bits and a single mismatch costs 8.21, so any error in a minimal overlap puts it under the floor. Sensitivity over all true overlaps ≥ 15 was 99.83%, and 0.6 keeps every one of those merges: on the regenerated benchmark, 0 of 0.5.3's 577,517 correct merges are forgone.

**Read the guarantee for what it is.** `α` bounds merging *unrelated sequence*, and there it holds with room to spare: 0 spurious merges in 40,000 uniform-random pairs at every read length from 50 to 300, and 0 in the 20,000-pair 2×150 case `test_unrelated_pairs_do_not_merge` pins. It is not a bound against real sequence, where two fragment ends can be genuinely homologous. The plausibility gate (§1.5) removes the *divergent* part of that population; what survives is near-identical repeat. On the hg38 benchmark 0.6 still merges 2,131 of ~385,000 pairs that have no true overlap (0.55%; 0.5.3: 4,757), and on 0.5.x 1,403 wrong merges per million remained even at a 100-bit threshold — every one a fragment whose two ends really are homologous, with the scan choosing the correct argmax over a region that genuinely matches. Raising `T` buys far less than the formula suggests, because past a point the score is measuring real similarity rather than chance. §3.4 gives the same population from the consumer's side: what `IS_FULL_FRAGMENT` does and does not assert.

**Why the default `α` is 10⁻⁶.** It reproduces 0.5.x's 28 bits at 2×150, and 28 minimized false positives plus false negatives on the 0.5.x benchmark: 6,603 errors per million pairs, rising monotonically to 13,584 at 34, 45,616 at 60 and 96,512 at 100 bits. The curve is steeply asymmetric because sensitivity falls much faster than the chimera rate does — going from 28 to 34 bits prevented 708 wrong merges and caused 7,689 missed ones, about 11:1, reaching 22.5:1 at 100 bits. Those are 0.5.x measurements (no gate), and the gate has since removed about half the wrong merges the sweep was trading against, which makes raising `T` a worse bargain, not a better one. The same scale prices a familiar knob: 60 bits is `ceil(60/1.9855) = 31` clean bases, fastp's `--overlap_len_require 30`, and at 2×150 it is `--alpha 2.6e-16`; on 0.5.x it landed within a rounding error of fastp's default operating point (0.597% chimera rate at 92.63% sensitivity, against 0.621% and 92.98%).

**Validation.** `α` and `e` are parsed from the decimal string typed into an exact rational (`exact`, `params.py`): `α` must lie in [10⁻³⁰⁰, 1) and `e` in [10⁻⁹, 0.75), and both must have a finite decimal form of at most 50 digits, because the file's prologue records the values used as decimal strings (§3.8). At `e ≥ 0.75` the mismatch weight is no longer positive — "overlapping" mates would agree no better than chance — and the lower bounds refuse a mistyped exponent rather than spending seconds building tables for it. A run in which no pair *could* merge (the floor exceeds what the longest read can score) says so at the end.

### 1.4 The error rate: a parameter with two roles

`e` enters the decision twice, and the two roles are different in kind (`params.py` module docstring):

- **In the score it sets strictness.** How much a mismatch costs relative to a match. The `α` bound on chance merges does *not* depend on `e`: under unrelated sequence the likelihood ratio averages exactly 1 whatever `e` the overlap hypothesis assumes. A larger `e` makes a mismatch cheaper, so it tolerates sequencing errors and repeat divergence alike.
- **In the plausibility gate it is a promise** (§1.5): a true overlap is refused with probability at most `α` *only if `e` is at least the library's real disagreement rate*. Set too low, true overlaps are refused — and kept whole, never merged wrongly.

**Why a parameter and not an estimate.** A per-library estimate was implemented and measured before it was dropped. Fed into the score, a noisy library's own higher rate softened the mismatch penalty and let *more* divergent repeats and short false read-throughs merge: on the truth panel's 3′-degraded sets, wrong merges went 560 → 741 at the estimated 0.035, against 560 → 240 at a fixed 0.01, and lost fragments rose on a 1%-error hg38 set. Clean libraries estimated low and rejected a few short true overlaps carrying two or more errors. The estimator also needed a buffered sample, a prior, and a caveat about sorted input. A fixed, documented `e` is simpler and was safer on the panel; the data are used to *check* it instead (§1.12).

The default 0.01 is 0.5.x's hidden `err_rate`, now documented. It holds on every full-scale bench: the true disagreement inside true overlaps measured 0 on the error-free chr22 and clean transcriptome sets and 0.0041–0.0049 on the noisy, fastp-trimmed and hg38 sets, all below 0.01. Production RNA libraries measured ~0.009 on 0.5.3's comparable statistic.

**Exact derivations.** `e = a/b` is an exact rational, so the weights and `T(N)` are computed with `decimal` (software, correctly rounded, 50 significant digits) and `dfit` with pure integers (§1.5); what crosses into either backend is two weights and two `int64` tables. No libm reaches a decision. Exact arithmetic lands on 0.5.3's weights at `e = 0.01` (33,311,170 and 137,813,407), which 0.5.3 had derived with `math.log2` and pinned per platform.

### 1.5 The plausibility gate

The score's argmax answers "which shift is best"; it cannot say whether the best shift is *believable*. The report's dominant failure is a long divergent repeat outscoring a short true overlap: case C01 aligns 122 bases with 19 mismatches and beats a clean 38-base true overlap. So the winner is tested once more, at the same `α`:

```
dfit[n] = max d  with  P(Binom(n, e) ≥ d) ≥ α        # exact integers, table over n
d_inf   = mismatches at W  −  positions where exactly one mate reads N
d_inf > dfit[n_W]   ⇒   W is implausible: the pair has no overlap
```

Only one shift can be the true one, so under the error model a true overlap is refused with probability at most `α`. **One tolerance, two errors:** at most `α` chance merges of unrelated sequence, and at most `α` true overlaps refused, per pair. At `e = 0.01`, `dfit` is 5 at n = 30, 7 at 64, 8 at 100, 9 at 122 and 10 at 150; C01's 19 in 122 is refused.

`dfit` is built exactly (`binom_cap`, `params.py`): with `e = a/b` and `α = A/B` the tail comparison `P(X ≥ k) ≥ α` becomes an integer inequality over the common denominator `bⁿ`, and because adding a trial adds at most one success, `dfit[n+1]` is `dfit[n]` or one more, so each `n` costs one exact step. A 10 kb read's table (capacity 16,384) builds in 0.41 s, once per run.

**Abstain, don't re-place.** An implausible winner marks a repetitive context, and nothing is searched for in its place. The alternative — take the best plausible shift instead — was measured: it re-placed 37–38% of the wrong merges it caught onto *another* wrong shift on the gene-disjoint holdout (9% on the development set). Abstaining removes that class by construction, and on the development set removed ~10% more wrong merges than re-placing with no added lost fragments; its cost is 145–271 re-merges forgone per 500k–1M pairs, where the true overlap was outscored and the pair is kept whole instead of merged.

**An `N` carries no information about agreement**, so a position where exactly one mate reads `N` does not count against plausibility (`_n_positions` in `_pymerge.py`, `n_positions` in `merge_core.hpp`). It still counts as a mismatch in the score — a no-call never equals a call — so which shift wins is unchanged; only the gate's verdict on it is. Without the discount, reads with N runs had ~1,500 correct merges per 200k refused, the one correctness regression the policy's robustness review found. `N` against `N` is a match in the scan and is left alone; `dfit` stays indexed by the overlap length.

**Sensitivity, in closed form.** A true overlap of `n` bases whose mates really disagree at rate `e′` is refused with probability `P(Binom(n, e′) > dfit[n])`. With the gate built for `e = 0.01` (`test_the_gate_refuses_a_true_overlap_with_probability_at_most_alpha`):

| true disagreement `e′` | n = 50 | n = 100 | n = 150 |
|---|---:|---:|---:|
| 1% | 6.9×10⁻⁷ | 8.4×10⁻⁷ | 4.2×10⁻⁷ |
| 3% | 0.07% | 0.32% | 0.58% |
| 5% | 1.2% | 6.3% | 13% |

which is why `e` has to be at least the library's real rate, and why the run reports what its data say about that (§1.12).

**Measured.** Across the eight full-scale benches (4.11M pairs, each under its primary contract), the gate refused 5,632 pairs and **none at the true fragment length**; every refusal on hg38 (2,946) was a pair 0.5.3 had merged wrongly. On the report's 19 cases at the default `e` it refuses C01, C02, C05, C09, C12, C15 and C18 (`TestReportCases`, fixtures in `tests/data/report_cases/`).

### 1.6 The decision

```
eligible  = every s ∈ [-(len2-1), len1-1]              (default)
          = s ≥ max(0, len1 - len2)                     (--adapter-trimmed, §1.7)
W         = argmax over eligible s of score(s), with floor T(len1+len2-1);
            nothing reaching the floor  ->  no overlap
W exists and d_inf(W) ≤ dfit[n_W]  ->  MERGE at W, one full-fragment record
otherwise                          ->  KEEP both mates as read (N policy applied)
```

`argmax`, not first-accept: the scan cannot be captured by a spurious short hit before it reaches the real offset. A chance 4-base hit scores 7.9 bits; a real 40-base overlap scores 79 and wins outright.

The argmax is a specified total order — maximize score, then minimize `s` — rather than whatever the loops happen to produce; §2.2 gives the order, the visiting sequence that realizes it, and why periodic sequence makes it necessary. Restricting eligibility removes shifts from that order without reordering the rest. Ties are settled by the order and not reported: no margin is computed.

The floor is the scan's starting incumbent. It begins at `T − 1` (`scan_eligible`, `merge_core.hpp`; `scan`, `_pymerge.py`), so a best shift below the floor is reported as no overlap at all (`overlap_len == 0`) rather than as a sub-threshold argmax, and at ~28 bits the incumbent prunes from the first shift visited (§2.3). The gate is applied after the scan to its winner alone — one table lookup, no state in the loop — and its verdict (`merge`, `none`, `implausible`) is what `find_overlap` returns (`overlap.py`); the unrestricted, ungated argmax survives only under the diagnostic name `scan_unrestricted`.

### 1.7 Read-through, and the `--adapter-trimmed` declaration

**Without the declaration, read-through is inferred, and that *is* overlap-based adapter removal.** A read contains adapter only when its insert is shorter than the read, so the mates overlap completely, the best shift is negative, and the merged record `[0, L)` excludes the adapter without it ever being matched against an adapter sequence. On the 0.5.x benchmark read-through fragments reconstructed at 100.00% in every length bin (230,815 pairs).

**With `--adapter-trimmed`, read-through is impossible.** After adapter trimming — or for reads clipped to the molecule, as khorana's simulator produces them — no read extends past its fragment, so an alignment implying one does cannot be the truth. The eligible shifts become those with inferred `L ≥ max(len1, len2)`, i.e. `s ≥ max(0, len1 − len2)`: not merely `s ≥ 0`, because with `len1 > len2` a shift in `[0, len1 − len2)` puts R1 past the fragment's end (`TestContractRange`). No threshold is involved. The restriction removes the false read-throughs that made up most of 0.5.3's lost fragments — a divergent alignment at a negative shift yields a "fragment" shorter than `--min-read-length`, and the pair vanishes — and on input where the declaration is true it measured better than every tuned read-through rule tried (the transcriptome fastp set: −715 wrong merges and +332 correct merges, against −632 / +249 for the best rule).

**The declaration is trusted, and checked.** Declaring it on raw reads is catastrophic — it forbids exactly the merges those pairs need (−231,000 correct merges on the 1M-pair hg38 benchmark) — so over the input's first 100,000 pairs a second, unrestricted scan counts pairs whose best alignment is a read-through reaching the floor, and a declared run warns when that exceeds 1% (`_WARN_READTHROUGH`, `src/zna/merge/cli.py`). Measured at full scale: 0–0.11% on honestly trimmed input, 2.3% on the raw transcriptome set and 23% on raw hg38. The window is the input's first pairs, counted from the start of the input rather than per chunk, so the check is identical at any thread count and chunk size. It is a diagnostic: nothing it finds changes a decision.

**What "honest" requires of the trimmer.** The declaration is only as good as the adapter removal behind it: it requires reads whose adapters were removed completely upstream. A read-through pair left with 1–3 bp of adapter can no longer align at its true shift, which is now a forbidden read-through; it is kept whole with its adapter, or, rarely, merged at a wrong length. fastp variants on the transcriptome set's noisy reads (500,000 pairs, 2×150; every variant with `--max_len1/2 150 --length_required 40`; fastp 1.3.6 and 1.1.0 gave identical numbers):

| fastp | passes | pairs left with adapter | adapter bases | sequencing errors kept |
|---|---:|---:|---:|---:|
| `--detect_adapter_for_pe --allow_gap_overlap_trimming --cut_tail --cut_window_size 1` | 1 | 42 (7 on both mates) | 60 | 1.982/kb |
| the same without `--cut_tail --cut_window_size 1` | 1 | 7 (all on both mates) | 22 | 1.999/kb |
| adapters first, then `-A --cut_tail --cut_window_size 1` | 2 | 7 | 21 | 1.982/kb |
| `--overlap_diff_limit 10`, with `--cut_tail` | 1 | 53 | 132 | 1.982/kb |
| untrimmed input, for scale | — | 11,275 | 423,712 | 2.00/kb |

`--cut_tail` runs before fastp's overlap-based adapter detection and, by trimming R2's last (adapter) base, hides R1's 1–2 bp overhang: 35 of the 42. Dropping it removes that class in one pass. The last 7 keep 1–3 bp on *both* mates (inserts 147–149, five of them with no sequencing error in the insert); fastp's overlap detection misses them itself, and no flag tried removes them (`--overlap_diff_limit` 10 without `--cut_tail` left 18; lowering the limit to 1 or 0 left 46 or 368). Our hypothesis, not verified: low-complexity inserts on which fastp accepts a full-length overlap. What dropping `--cut_tail` costs is 3' quality trimming, which here removed 0.9% of sequencing errors (about 2,700 of 300,000) by shortening about 60,000 reads; an aligner such as STAR soft-clips low-quality ends anyway.

zna on the single pass without `--cut_tail` (0.5.3 → 0.6, `MERGE_BENCHMARK_RESULTS.md` §9):

| contract | wrong merges | lost | correct merges forgone / gained | adapter bases emitted |
|---|---|---|---|---|
| declared | 1,421 → 664 | 16 → 0 | 7 (0.0019%) / 179 | 0 → 8 (3 pairs) |
| undeclared | 1,421 → 750 | 16 → 15 | 0 / 0 | 0 → 0 |

The 7 forgone merges are the 7 residual pairs: 4 become wrong merges and 3 are kept with their adapter. Under the declaration with `--cut_tail` kept (one pass), 42 are forgone (0.011%, over the plan's 0.01% limit) and 47 adapter bases are emitted. Declaring the single pass without `--cut_tail` is better on net than not declaring it, and running undeclared is always safe. Trimming stays fastp's job; the read-through check is the per-library signal that it did it.

### 1.8 Merge

`L = s + len2` is the fragment. R1 supplies `[0, min(len1, L))` from its 5' end — its copy of the overlap, carrying the consensus — and revcomp(R2) supplies whatever remains, which is by construction outside the overlap (`_build_merged`, `_pymerge.py`). The record has length `L` identically for every geometry, including read-through, where the adapter falls outside `[0, L)` and is discarded. A merged read is a genuine full molecule, so it is length-filtered on its own (§1.11) and carries both fragment ends (§3.4).

If `--npolicy trim3` has cut a mate at an unrescued `N` so far that the two no longer tile the fragment (`len1′ + len2′ < L`), the merge verdict cannot be acted on and the pair is kept (§1.9). Nothing is re-scored: trimming cuts 3' ends, which is where a normal overlap lives, so a re-scan would refuse merges it had ample evidence for a moment earlier.

### 1.9 An unmerged pair is kept whole

A pair that does not merge is emitted as its two input mates, changed by nothing but the N policy — no bases removed from the overlap, no bases rewritten. 0.5.x instead ran a *trim band*: a best shift scoring between 8 and 28 bits kept both mates and split the redundant overlap between their 3' ends. 0.6 removes it, with `--threshold-trim`, the balanced split, the trim guard, trim-path consensus and the `PROV_TRIMMED` provenance bit (§3.7).

**Why.** khorana trains on one randomly chosen mate of an unmerged pair and wants it whole. The band's benefit was small and its harm concentrated: it removed ~0.55 duplicated bases per pair (550,656 redundant copies per million chr22 pairs, per khorana's chr22 merge review §3), while on the chr22 simulation it caused every wrong trim — 1,454 per million pairs, deleting 23,823 real positions — and 1,755 substitutions into kept mates through trim-path consensus. At full scale 0.5.3 made 7,225 wrong trims and 14,366 kept-mate substitutions over the eight benches; 0.6 makes 0 of each by construction, and no kept mate is shortened anywhere except at an `N`.

**The cost** is the redundant overlap the band used to remove. On the 0.5.x hg38 benchmark's accounting, unmerged pairs carried 283,838 duplicated fragment bases per million pairs before trimming and 28,074 after — about 23 duplicated bases per 10,000 unmerged bases untrimmed, against 2.25 with the band and 85.8 for fastp, which has no overlap trim at all. Other uses of overlap trimming — variant calling, coverage — are served after alignment by the tools that need them.

### 1.10 The overlap consensus

Where the mates overlap they are two independent reads of the same physical base, so a disagreement means exactly one of them is wrong. Which one is not a judgement call — the sequencer already said, in the two Phred scores. With `pᵢ = 10^(-Qᵢ/10)` and "exactly one is wrong",

```
P(R1 is the wrong one) = p₁(1-p₂) / (p₁(1-p₂) + p₂(1-p₁))
```

so the consensus base is the higher-Q call, and the posterior error of *that* call is the expression above — which is worse than the winner's own Q, because a contested base is less certain than an uncontested one. For well-separated qualities the derated value is close to `Q_win - Q_lose`: a Q40 base contested by a Q20 base is emitted at ~Q20, not Q40. On equal quality R1 stands, derated. Nothing to tune, and no quality cutoffs.

The posterior is precomputed as a **256×256 byte table indexed by raw quality byte** (`_build_disagree_table`, `params.py`), built once in Python and passed to whichever backend runs, so the two implementations cannot disagree by a quality unit on some cell. The table is 256×256 rather than 94×94 (the legal Phred+33 range) because quality bytes come from a FASTQ file and nothing upstream guarantees they are legal: a 94×94 table would make a malformed byte an out-of-bounds read in C++ and an `IndexError` in Python, where a full table makes it defined. Both backends reject a table that is not exactly 65,536 bytes (`src/zna/merge/_accel.cpp`).

Measured against ground truth on the 0.5.x benchmark's merged records (the merge path and its consensus are unchanged in 0.6), this recovers **90.35%** of the overlap errors that were recoverable at all (a position where both mates are wrong is not), reducing 182,184 errors under an R1-wins rule to 84,469 against an oracle floor of 74,037, and leaving 895 of 577,275 records worse than doing nothing — a ratio of 109:1.

**N rescue.** An `N` is a no-call: it carries no base information, so a real call on the other mate beats it whatever the two quality scores say, and the rescued base keeps the surviving mate's own quality rather than a contested-base derating — there was no contest. Only `N` is rescued; the IUPAC ambiguity codes do carry partial information and are left alone. Rescue does not touch the *scan* — an `N` still counts as a mismatch when a shift is scored — so which shift wins is unchanged.

**The consensus is written into a merged record's R1 copy and nowhere else.** A merged record takes the overlap from R1 and R2 contributes only outside it, so R2's copy is never emitted and is never written. A kept pair gets no consensus at all: nothing about it depends on the alignment being right, and an alignment too suspect to merge on is too suspect to rewrite bases on. That was measured under 0.5.x, when kept pairs could still carry a detected overlap: of the 3,068 on the 1M-pair benchmark **none had found the true shift** and 97.3% had no true overlap at all, and writing the consensus there would have turned 1,379 correct bases wrong to fix 78.

**Kept means as read, including after a merge verdict.** When `trim3` turns a merge verdict into a kept pair (§1.8), R1 is re-derived from the input with only the N policy applied, and none of the consensus — substitutions, derated qualities, rescues — is emitted or counted (`_process_pair_ex`; `process_pair` in `merge_core.hpp`). 0.5.x emitted the consensus-rewritten R1 in that case: 167 kept pairs on the truth panel's N benches, 10 of their substitutions to a wrong base. `test_a_merge_verdict_kept_by_trim3_emits_r1_as_it_was_read` pins the fix.

### 1.11 Pair integrity

`min_read_length` is an orthogonal QC filter applied to the emitted records, after any merge. It is applied **all-or-nothing to an unmerged pair**: if either mate falls below the floor, both are dropped. A lone surviving mate would be encoded as a spurious "single" — a full molecule with two true endpoints — which is precisely the supervision signal the corpus exists to carry (§3), so a half-pair emitted alone is not merely a lost read but a fabricated fragment. A merged record is a genuine full molecule and is therefore filtered on its own. Kept mates are the input, so on input that has already been length-filtered at the same floor, only `trim3` can put one under it.

### 1.12 What a run reports about its own parameters

Every decision parameter is fixed before the first pair is read. The input is only ever *checked* against them, by statistics that ride along in the chunk loop and change nothing (`run_warnings`, `_assemble_stats` in `src/zna/merge/cli.py`, shared by `zna merge` and `zna encode --merge-pairs`). Every value is finite and of a fixed type whatever the input, because hulkrna's cohort gather rejects `Infinity` and type changes.

- **`detected_overlap_mismatch_rate`** — informative mismatches over informative compared positions, over *every* overlap the scan detected (score ≥ `T`), merged and refused alike, before the gate. Before the gate because the gate is what a too-low `e` makes wrong: a rate measured on its survivors could never exceed the `e` that filtered them. It is a check, not an estimate, and it errs both ways: repeats that reached the floor inflate it on clean genomic libraries (hg38: 0.0051 detected against 0.0041 true), while on degraded ones the most divergent true overlaps never reach the floor, so it can read low (a 5% 3′-ramp set: 0.0355 against 0.0385).
- **`expected_refused_true_overlap_fraction`** — what that rate *costs* at the `e` in use: the closed form of §1.5 averaged over the histogram of detected overlap lengths (`detected_overlap_length_histogram`),

  ```
  Σₙ count[n] · P(Binom(n, rate) > dfit[n])  /  Σₙ count[n]
  ```

  summed as a direct upper tail in 50-digit `decimal`, so a tiny probability keeps its digits (`refusal_probability`, `expected_refused_fraction`). It treats every detected overlap as true and disagreeing at the detected rate, so it inherits that rate's biases. **The run warns above 0.1%** (`_WARN_REFUSED`): on the truth panel's 46 benches only the extreme 5% 3′-ramp set crosses it (0.40%; the next highest is 0.017%), and every full-scale bench reads ≤ 4×10⁻⁹. The warning states the trade rather than just the fix: raising `--error-rate` recovers the refused pairs, which are kept whole and never merged wrongly, but it also cheapens every mismatch in the score, so more short or divergent overlaps merge, false ones included — on the 3′-ramp sets, 240 wrong merges at 0.01 against 745 at the suggested 0.036. A trigger on "detected rate above `e`" was tried first and fired on 12 of the 46 benches, ten of them expecting under 0.02% refused.
- **`readthrough_check_strong_fraction`** over `readthrough_check_pairs` — the `--adapter-trimmed` check of §1.7, reported with or without the declaration; only a declared run warns on it.
- **`implausible_refused`** — pairs the gate refused, true overlaps and repeats together.
- **`overlap_mismatch_rate`** — mismatches per aligned base over the *merged* overlaps, after the gate, counting a one-sided `N` as a mismatch. It is the sensitive per-base degradation channel, and it cannot test `e`, because the gate filtered it.

The prologue of a `.zna` written by `encode --merge-pairs` records the parameters themselves (§3.8), so a file carries the policy it was made under and the run's JSON carries what the data said about it.

## 2. The kernel: determinism, fixed point, and the search

The scan answers exactly one question — where does revcomp(R2) sit on R1's axis — by scoring every candidate offset `s` and taking the best. Two properties make that answer *reproducible* rather than merely repeatable: the score is an integer, and the argmax is a specified total order. Most of what follows falls out of those two.

### 2.1 Scores are integers

A shift's score is a log-likelihood ratio in bits (§1.2), but it is computed as

```
score_q = n * match_q - d * step_q          # int64, SCALE units per bit
```

with `n` the overlap length, `d` the mismatch count, and `SCALE = 2**24`. No float takes part in a comparison, in the per-shift bail bound, in the floor or in the plausibility gate, so the argmax cannot depend on the compiler, the optimization level or `-ffast-math`. That is what turns "the two implementations agree" from an approximate claim into an exact one: they can be asserted equal shift for shift and byte for byte, because neither of them rounds anything.

The weights are derived **once, in Python** (`weights_q`, `src/zna/merge/params.py`), from the exact rational `e` with correctly rounded 50-digit `decimal` arithmetic:

```
match_q = round_half_even(log2((1 - e) / 0.25) * SCALE)      #  33_311_170 at e = 0.01
step_q  = match_q + round_half_even(log2(0.75 / e) * SCALE)  # 137_813_407
```

and crossed as integers, together with two `int64` tables: the per-pair floor `T_q[N] = to_q(log2(N/α))` (§1.3) and the gate's `dfit[n]` (§1.5). `math.log2` is not correctly rounded and libm differs between platforms, so deriving any of these on the C++ side — or with floats on the Python side, as 0.5.x did for its weights — would invite a 1-ULP disagreement that silently changes a corpus. Exact arithmetic lands on the same two weights 0.5.x pinned per platform, and the tests pin them and golden values of both tables (`TestDerivations`). The weights are echoed into the JSON stats (`score_scale`, `match_q`, `step_q`), and `α` and `e` into the stats and the file's prologue as exact decimals, from which every floor is reproducible. The 256×256 consensus posterior table (§1.10) is passed in for the same reason — it is built with `pow`/`log10`, and both backends reject a table of the wrong size.

**The tables are grown, never capped.** Both are indexed by read geometry, so they are built for a *capacity* — the longest read they cover, starting at 256 bases — and doubled when a longer read turns up (`MergeParams.ensure`). A table's prefix never changes when it grows, so where growth happened leaves no trace in the output (§2.7). Building them is the one cost of a long read: to capacity 16,384 (a 10 kb read) `dfit` takes 0.41 s and `T` about 1.2 s, once per run.

`step_q` is quantized as the *sum* of the two quantized weights, not independently, so that `n*match_q - d*step_q` and `(n-d)*match_q - d*mismatch_q` agree exactly. `int64` is required rather than stylistic: `match_q ≈ 2**25`, so `n * match_q` leaves `int32` at n = 64, and a 150 bp overlap needs 33 bits.

**Why `SCALE = 2**24`.** Quantizing the weights and the floor perturbs the score by at most `(n + 2d + 1)/2 * 2**-24` bits relative to the floor, so the merge decision `score_q ≥ T_q[N]` could in principle differ from the exact real-valued one where the true score sits within that of `log₂(N/α)`. Whether it ever does is exhaustively enumerable over integer `(n, d)` for a given `(e, α, N)`; `TestFixedPointScale` in `tests/test_merge.py` runs the enumeration to n = 4,000 for nine `(e, N)` settings, and `params.py`'s docstring reports the wider one below. The scale was chosen against 0.5.x's two fixed thresholds; smallest overlap `n` at which the fixed-point and float decisions differ at all:

| SCALE | at 8 bits | at 28 bits |
|---|---:|---:|
| 2^16 | 2,718 | 3,299 |
| 2^20 | 4,377 | 2,575 |
| **2^24** | **34,632** | **32,830** |
| 2^30 | 176,375 | 174,573 |

(The ordering is not monotonic in SCALE: it depends on where the near-threshold `(n, d)` pairs fall relative to each rounding.) 2^20 — the obvious "millionths of a bit" choice — disagrees at an overlap of 2,575 bases, which is not comfortably out of reach. Re-measured for the per-pair floor — `α = 10⁻⁶`, `N` = 99, 199, 299, 599 and 2,047, `e` = 0.00016, 0.001, 0.0087, 0.01, 0.03 and 0.1 — no decision differs at any overlap up to 10,000 bases; the smallest disagreement among those 30 settings is at n = 10,951 (`e` = 0.0087, `N` = 2,047), and 22 of them show none up to 20,000. That is a statement about the settings enumerated, not about every rational `e`; what holds for every setting is the bound itself, and the gate is an integer comparison (`d_inf ≤ dfit[n]`) that no scale affects. So no read-length cap is needed anywhere in the tool, and `int64` overflows only past 2.8×10¹¹ bases.

### 2.2 The argmax is a total order

> **Maximize `score`; among ties, minimize `s`** — the leftmost, most read-through alignment.

This is a specification, not an artifact of iteration order (the header comment of `merge_core.hpp`; `scan` in `_pymerge.py`), and it is what lets a rewritten kernel be tested for exact equality instead of the weaker "returned *an* argmax". Two facts make the two keys sufficient. Ties across *different* overlap lengths need `Δn * match_q == Δd * step_q`, whose minimal solution is `step_q / gcd(match_q, step_q)`; that gcd is 1 for the shipped weights and for every `e` in {0.001, 0.005, 0.01, 0.02, 0.05}, so `Δn` would have to exceed 1.3×10⁸. Ties therefore only ever occur at equal `n`, and `n` never discriminates.

The visiting order realizes the rule directly. The scan walks the plateau first — every shift achieving the maximal overlap `nmax`, ascending in `s` — and then the two flanks in lockstep at decreasing `n`, read-through side (`s = n - len2`) before the normal side (`s = len1 - n`). At any fixed `n` that is ascending in `s`, and improvement is strict `>`, so the first-visited member of a tie keeps the win. **Do not reorder these loops.** Swapping the two flanks changes the winner on every tied pair — and with it which bases a merged read is built from — while leaving every random-sequence test green: random sequence essentially never ties (a sweep of 7,000 random and adversarial pairs produced exactly zero), so the tie fixtures have to be constructed deliberately.

The `--adapter-trimmed` contract (§1.7) is two changes to this visiting order and nothing else: the plateau shrinks to its last shift, and the read-through flank is never visited, since every shift on it is below the plateau's lowest. Removing shifts from an ordered sequence does not reorder the rest, so the total order holds over the eligible set unchanged (`TestArgmaxTotalOrder` runs under both contracts).

### 2.3 Pruning is exact in integers

The score is monotone decreasing in `d` alone, which gives two bounds.

- **Outer.** Shifts are visited in decreasing `n`, so once `n * match_q <= best` no remaining shift can win and the whole scan stops.
- **Inner.** `score_q > best` iff `d * step_q < ceiling - best` iff `d <= (ceiling - best - 1) / step_q`, where `ceiling = n * match_q`. That budget is computed once per shift and the comparison loop bails the moment it is exceeded.

Both sides compute the same integer because `ceiling > best` is checked first, so the numerator is non-negative and `step_q` is positive — the range where C++ truncating division and Python floor division agree. Computing the budget as `int((ceiling - best) / step)` in floating point would put a platform-dependent boundary back into control flow, which is the one place §2.1's guarantee cannot survive it.

Pruning is consistent with the tie rule for free. Rejecting on `ceiling <= best` discards only shifts that could at best *tie* the incumbent, and a tie always loses under strict `>`. The incumbent's initial value is the pair's floor minus one, `T_q[N] − 1`, which is what makes a sub-threshold best shift come back as "no overlap" (§1.6).

**What the higher floor bought.** 0.5.x started the incumbent at its 8-bit trim threshold; 0.6 starts it at ~28 bits. Counted on 1M chr22 pairs, that trims the work only slightly — 191.7 shifts and 10,277 compared bases per pair at 8 bits, 187.5 and 10,104 at the floor (−2.2% and −1.7%) — yet the scan takes 15% less time (0.448 → 0.379 µs/pair). The work saved is mostly short, scalar, branchy tail shifts; that attribution is an inference, the counts are measured. The `--adapter-trimmed` contract halves the work outright: 94.2 shifts and 5,096 bases per pair.

### 2.4 The inner loop compares raw bytes

```c
const uint8_t* a = s1   + (s > 0 ?  s : 0);      // a shift is just a pointer offset
const uint8_t* b = s2rc + (s < 0 ? -s : 0);
constexpr int GROUP = 16 * BAIL_VECTORS;         // 48 bases on x86, 64 on aarch64
for (; k + GROUP <= n; k += GROUP) {
    d += neq16x<BAIL_VECTORS>(a + k, b + k);     // ONE reduction per group
    if (d > dmax) return REJECT;
}
for (; k + 16 <= n; k += 16) {                   // keeps the byte tail under 16
    d += neq16(a + k, b + k);
    if (d > dmax) return REJECT;
}
for (; k < n; ++k) d += (a[k] != b[k]);          // scalar tail
```

`neq16x<V>` counts differing bytes across `V` consecutive 16-byte windows, accumulating the per-lane equality flags in a vector register and folding them **once for the whole group**: `vceqq_u8` + `vaddq_u8` then one `vaddvq_u8` on NEON, `_mm_cmpeq_epi8` + `_mm_sub_epi8` then one `_mm_sad_epu8` on SSE2. Sixteen bytes is baseline on every target — NEON on aarch64, SSE2 as part of the x86-64 base ISA — so there is no `-march` flag and no runtime dispatch, and where neither is available the vector blocks compile out and the scalar tail does the whole overlap for the same result. Because a shift is a pointer offset there is no packing step, no cross-word realignment, no guard word and no lookup table, and every loop guard is `k + <step> <= n`, which is the only thing keeping the loads inside the record.

**`psadbw`, not `pmovmskb` + popcount, is what makes the x86 path fast**, and the reason is worth stating because the obvious kernel is a trap. POPCNT is SSE4.2-era and this extension is compiled for baseline x86-64, so `__builtin_popcount` there is not an instruction: GCC emits `callq __popcountdi2@plt`. Through 0.5.1 that call sat in this loop, twice per 32 bases, and cost it 1.88× — the byte-SIMD kernel was only 1.33× the scalar one on x86 against 2.3× on aarch64. `psadbw` is baseline SSE2 and is the exact analogue of `vaddvq_u8`, so grouping the reduction removes the call rather than working around it. Bail granularity is a hardware property and is set per ISA (`BAIL_VECTORS`); the 16-byte step between the group loop and the byte tail is what makes a wide group affordable, since a 48-base group would otherwise leave up to 47 bases — a third of a 150 bp read — to the scalar loop.

**Byte comparison is not an approximation of the reference semantics — it *is* the reference semantics.** `N` vs `N` earns a full match, `N` vs `A` is a mismatch, IUPAC codes compare as themselves (`reverse_complement` passes anything outside ACGTN through uncomplemented, deliberately), and any byte at all is defined. There is no purity test, no dispatch, no second code path to keep in sync, and no class of input on which the fast path and the oracle can disagree. A 2-bit packed kernel cannot have that property — `N` would collapse onto a real base and start manufacturing evidence — and would need a packer, bit realignment and a purity dispatch to fake it. (The container's 2-bit alphabet, §4.1, is a separate matter: the merger never packs, and `N` policy is applied at encode time.)

Measured over 50,000 real pairs, full pruned scans, every variant checked against the shipped kernel's `(s, n, d)` on every pair, zero mismatches throughout (Apple M-series, aarch64/NEON, Apple clang, `-O3 -std=c++17`, min-of-N):

| variant | µs/pair |
|---|---:|
| numba JIT (pure-Python-source baseline) | 2.633 |
| scalar C++, direct transliteration | 1.075 |
| 2-bit packed, SWAR packer, fused flanks | 0.535 |
| byte SIMD, 16 B vectors, bail every 16 | 0.534 |
| **byte SIMD, 16 B vectors, bail every 32** | **0.470** |
| byte SIMD, 16 B vectors, bail every 64 | 0.515 |
| byte SIMD, bail 32, fused flanks | 0.555 |

Bail granularity, not vector width, is the variable that matters: the scan is rejection-dominated (roughly 0.32·n comparisons per rejected shift), so with one reduction per vector 32 bases beat both 16 (too much branching) and 64 (too much work past the point of rejection). The grouped reduction below moved that optimum: re-measured in 0.5.3 on an Apple M3 Max, bail 64 runs at 0.416 µs/pair against 0.506 at 32, and `BAIL_VECTORS` is 4 on aarch64 (`docs/ROADMAP.md`, "Closed by measurement in 0.5.3"). Fusing the two flank shifts helps a packed kernel and hurts this one — it doubles register pressure and defeats the early-exit ordering.

**The same table on x86-64** (Xeon E5-2680 v3, Haswell; g++ 8.5, `-O3 -std=c++17`, no ISA flags), taken in 0.5.2 and the reason the kernel above has three loops instead of two:

| variant | µs/pair |
|---|---:|
| scalar C++, direct transliteration | 4.34 |
| 0.5.1 kernel: `movemask` + popcount, bail 32 | 3.140 |
| `psadbw`, bail 32 | 1.747 |
| `psadbw`, bail 48 | 1.671 |
| **`psadbw`, bail 48, + 16-byte step** | **1.539** |
| AVX2 32 B vectors, `movemask` + popcount, bail 32 (`-march=native`) | 1.556 |

Two things to read off it. The 0.5.1 kernel gained only **1.33×** over scalar here against **2.29×** on NEON, which is the popcount call. And the baseline-SSE2 kernel *beats* the AVX2 one, which is why no AVX2 path or runtime dispatch is built — with the reduction fixed there is nothing left for the wider vector to win. `docs/ROADMAP.md`, "Closed by measurement in 0.5.2", has the rest of the sweep.

The reference backend runs the same search with mismatches accumulated branchlessly in blocks of 8 and the bail tested once per block; the result is bit-for-bit identical either way, since overshooting `dmax` inside a block still rejects. A stride bug there (`k += 7`, a wrong `lim`) changes 6.34% of scores and 0.26% of 0.5.x's merge/trim/keep decisions on real data while passing every test that uses clean overlaps, so both loops have a dedicated test that sweeps a single mismatch across every position of a block, across the vector boundary and into the tail.

### 2.5 The contract and the gate in the kernel

The 0.6 decision (§1.6) adds three things to the scan — a per-pair floor, an eligible range and a plausibility test — and each was placed where it costs nothing in the loop.

- **The floor is the starting incumbent**, read from `T_q[len1 + len2 − 1]` once per pair (`decide`, `merge_core.hpp`). It is not a comparison inside the loop at all; it is the value §2.3's budget is computed against.
- **The contract is a template parameter**, not a runtime test in the flank loop: `scan_eligible<bool AdapterTrimmed>` is instantiated twice and `scan` dispatches once per pair. With `if (!adapter_trimmed)` inside the loop the undeclared scan measured 6% *slower* than 0.5.3's despite the higher floor; as two instantiations it is faster. Measured with non-inlined wrappers, a runtime-bool scan is 28% slower undeclared and 12% slower declared.
- **The gate is one table lookup on the winner**, after the scan: `W.mismatches − one_n > dfit[W.overlap_len]`. It adds no state to the scan loop. The one-sided-`N` count it needs comes from `n_positions`, which is gated on two `memchr` calls over the overlap slices, so an N-free overlap — nearly every one — costs two vectorized searches rather than a counting loop.

That shape is why the gate was built as abstention (§1.5). Policies that *re-place* an implausible winner, or veto shifts inside the scan, need either a second scan or extra incumbents carried through the loop; the prototype of that design measured 2.4–3.6× 0.5.3's scan time in its specified "lazy" form and needed a restructured one-pass loop to get back to parity; 0.6 needs neither (`docs/ROADMAP.md`, "Decided against").

The table lookups are in range by construction: every caller guarantees `max(len1, len2)` is within the tables' capacity (`Tables::capacity`), so `N ≤ 2·cap − 1 < t_len` and `n_W ≤ cap ≤ dfit_len − 1`. A chunk that meets a longer read stops in front of it rather than reading past a table (§2.7).

**Measured, compiled kernel, Apple M3 Max, clang -O3, µs/pair** (0.5.3 and 0.6 compiled into one driver, each with its own weights, which are identical):

| input | contract | scan 0.5.3 → 0.6 | `process_pair` 0.5.3 → 0.6 | `merge_chunk` 0.5.3 → 0.6 |
|---|---|---|---|---|
| chr22, 1M pairs | declared | 0.455 → 0.301 (−34%) | 0.667 → 0.330 (−50%) | 0.795 → 0.458 (−42%) |
| chr22, 1M pairs | undeclared | 0.443 → 0.376 (−15%) | 0.667 → 0.509 (−24%) | 0.792 → 0.633 (−20%) |
| truth panel, trimmed | declared | 0.559 → 0.340 (−39%) | 0.819 → 0.359 (−56%) | 0.929 → 0.471 (−49%) |
| truth panel, raw | undeclared | 0.519 → 0.435 (−16%) | 0.790 → 0.611 (−23%) | 0.873 → 0.689 (−21%) |

The undeclared gain is the floor alone: at the same floor 0.6's undeclared scan does exactly 0.5.3's work, with 0 result mismatches on 1M pairs and the same time. The `--adapter-trimmed` check (§1.7) runs a second, unrestricted scan on the first 100,000 pairs of a declared run; those pairs cost 0.703 µs against 0.5.3's 0.667 (+5.4%), and with the check on, a declared chr22 chunk still runs at 0.463 against 0.795.

### 2.6 Two backends, one specification

`src/zna/merge/_pymerge.py` is the **reference oracle, not a fallback**. It is plain Python — no JIT, nothing between the reader and the algorithm — about 50× slower than the compiled backend, and that is the correct trade: speed there would only buy the ability to be wrong in the same way as the thing it checks. It is never deleted and never optimized at the cost of clarity, because it is what the accelerated backend is *defined* to agree with, so it has to stay readable enough to be believed.

`src/zna/merge/backend.py` selects between them by name, validating that a backend exposes the full required set (`scan`, `overlap`, `process_pair`, `merge_chunk`, `merge_chunk_records`, `split_records`) and declares the contract its callers speak (`POLICY_ABI`, 2 in 0.6) before returning it, and resolving on first use so importing the package costs nothing. The marker exists because 0.6's argument lists are not 0.5.x's: a compiled extension left over from an older tree would be called with the right *number* of arguments meaning different things, so it is refused exactly as if it had not been built. `src/zna/merge/overlap.py` is a pure dispatcher over it. The CLI's `--backend {auto,accel,python}` makes either side first-class, and `auto` **refuses to run on the reference kernel**: a silently correct 50× slowdown at cluster scale is indistinguishable from a slow node and burns the allocation before anyone looks. The library entry point does not refuse, and the JSON stats record which kernel actually ran.

What the arrangement buys is enforced by differential tests at every level: identical `(shift, score_q, olen, diff)` from `scan`; identical verdicts from `overlap`; identical record tuples, counters and provenance bytes from `process_pair`; and from `merge_chunk`, an identical blob, identical consumed byte counts, identical counters, identical histograms and an identical capacity stop. Invalid input is held to the same standard — an unknown N-policy code, weights or floors past `int64` safety, a malformed table, lines ending in several carriage returns, a desync on a non-UTF-8 read name — and must fail or succeed identically in both (`TestInputValidationAgrees`). Those are equality assertions rather than "an argmax" assertions, which is only possible because of the integer score and the specified order. Two details keep the suite from being circular or blind: tests that go through the public API are parametrized over *every* available backend, since otherwise the oracle goes unchecked in exactly the environment that ships; and the tie fixtures build both plateau ties (periodic content on unequal-length mates) and flank ties (equal-length periodic mates held mutually out of phase), the latter being the only construction that separates the two flanks' visiting order. The differential catches defects of a kind review reliably misses — a compiled backend that threw on reads over 1024 bp where the reference merged them, a merged-name buffer sized from the read arena, which overflowed the heap on any FASTQ whose headers outran its reads, and, in 0.6's port, the five malformed-input disagreements listed above — three where the compiled side was wrong, two where the reference was too lax.

Beyond the suite, the 0.6 port was held to the reference on 980,000 fuzzed pairs through `process_pair` and 725,000 through the chunk functions at many cut schedules (adversarial geometry, ties, `N` runs, IUPAC and junk bytes, synthetic tables reaching every verdict branch), plus an exhaustive sweep of every pair of reads up to 4 bases over `ACGN`, with 0 differences once those five were fixed, and a planted-bug check confirmed the harness caught each of six deliberate defects. On the 245k-pair truth panel `panel_eval.py --backend accel` and `--backend python` produce the same pair-level ledger. `scripts/merge_bench/asan_scan.cpp` runs the core under AddressSanitizer and UBSan with every table allocated at exactly its capacity, so an index one past it hits a redzone.

### 2.7 Layering and the consumption protocol

Three layers, and the boundaries are load-bearing.

- **Core** (`merge_core.hpp`) — `scan`, `decide` and `process_pair` over `const uint8_t*` + length, writing into a caller-owned scratch arena. No I/O, no Python objects, no FASTQ. It is header-only and dependency-free so it can also be compiled into a sanitizer driver that cannot link against Python, and so a second consumer can reuse it without a second copy of the algorithm.
- **Adapter** (`fastq_chunk.hpp`) — `merge_chunk`: raw FASTQ text in, formatted FASTQ text out, plus counters and four histograms (emitted length, admitted overlap length, inferred insert, detected overlap length). `merge_chunk_records` is the same pass returning record offsets instead of text, which is what `zna encode --merge-pairs` consumes. It knows nothing about the scoring rule, and the core knows nothing about FASTQ.
- **Orchestration** (`src/zna/merge/cli.py`) — reading, chunking, threading, writing, statistics.

All three levels are exposed across the Python boundary; the fine-grained ones exist so failures localize, and `merge_chunk` is what production calls, because it captures the parse, the scan, the consensus, the construction, the formatting and the histograms in one GIL-released call. Only `int64`s, two `int64` tables and the byte table cross that boundary, so no float ever does, and `merge_chunk` is a pure function of its arguments — no globals, no clock, no RNG — which is what makes it fuzzable, safely callable with the GIL released, and byte-deterministic.

`merge_chunk` takes an explicit `(buffer, start, end)` range for each stream plus a `base_index` (`merge_chunk` in `_pymerge.py` and `_accel.cpp`). The explicit ranges, rather than sliced buffers, are what let worker threads share one immutable buffer per stream with no copy (§2.8). `base_index` numbers the pairs from the start of the input, which is what keys both `--npolicy random`'s position-derived substitution and the read-through check's first-100,000-pairs window to the input rather than to the chunking.

**The consumption protocol: whole pairs only, with a consumed count per stream.** `merge_chunk` merges pairs until either range stops yielding a complete record, and reports how many bytes it took from R1 and from R2 *separately*, so the two streams may carry different leftovers and Python never has to scan for record boundaries. A partial record at the end of a buffer is not an error — it is simply not consumed. At EOF the caller asserts that **both** buffers came out empty.

That protocol exists to make one specific silent data loss structurally impossible. A merger that consumed `min(records1, records2)` pairs and returned success would drop the trailing R2 records whenever R1 ran out first — and the R1/R2 name-sync check cannot catch that, because comparing base names cannot see records that were never read. Here the dropped records are still sitting in the caller's buffer, and the caller looks. The two ways that happens are diagnosed apart, since a wrong message sends the next person to the wrong file (`_check_drained`, `src/zna/merge/cli.py`; pinned by `test_a_truncated_final_record_is_rejected` and `test_unequal_read_counts_are_rejected`):

```
truncated FASTQ record at the end of <stream>        # leftover bytes, no complete record
<other> exhausted before <stream> (unequal read counts)   # leftover whole records
```

The threaded driver cuts chunks at `min(k1, k2)` whole records per stream, which is the same hazard shape — and is safe for the same reason, because whatever it does not hand to a worker stays in the buffer for the EOF check.

**The capacity stop.** The policy tables cover reads up to a capacity (§2.1). A chunk that meets a pair with a longer read does not consume it: it stops in front of it and returns `need`, the read length the tables must cover. The driver grows the tables — on the main thread only, by building new ones, never resizing an array a worker may be reading — and calls again from where the chunk stopped. Because a table's prefix is final, the output is identical whether and wherever that happens (`TestTableGrowth`).

### 2.8 Deterministic output under threading

Because `merge_chunk` releases the GIL for its whole duration, `--threads` are real worker threads rather than processes: no fork context, no pickling of chunks and blobs, no per-worker globals, no broken-pool handling. Each stream also gets one prefetch thread, so a blocking read overlaps merge work instead of stalling it. Chunks are cut to whole records with `split_records` and handed to workers as `(buffer, start, end)` into the stream's immutable `bytes` buffer (`_drive_threaded`, `src/zna/merge/cli.py`), so a chunk costs no copy and workers share the buffer safely. Memory is therefore one buffer per stream plus the submit window of 2×threads chunks in flight — not a per-thread copy of the input.

**Only a chunk that stopped for capacity keeps its input.** The window holds futures and nothing else, and a worker hands its buffers back only when it stopped short (`_merge_job`). The stream reader makes a new ~2 MB buffer about once per chunk, so a window that also held each chunk's arguments pinned up to twice its length of them: during the 0.6 port, peak footprint on 1M chr22 pairs went 30 / 69 / 194 MB at 1 / 4 / 16 threads. As built it is 26–34 MB at 1, 4 and 16 threads, against 0.5.3's 27–33 MB, with byte-identical output at every count.

**Blobs are written in submission order** (the `drain` loop of `_drive_threaded`), unconditionally and with no flag: futures are drained from the head of a bounded window, so chunk *i*'s output always precedes chunk *i+1*'s. Chunks are independent, so ordering costs only head-of-line blocking bounded by the variance in per-chunk compute time, a few percent for fixed-size chunks of Illumina reads. What it buys is that the output file is a pure function of the input and the parameters — identical at any thread count and any chunk size — which is the actual requirement for training data, and makes any future corpus defect bisectable.

The test suite asserts the write guarantee directly: `test_the_output_and_the_diagnostics_ignore_threads_and_chunking` byte-compares the whole output file and compares the complete statistics dict — every counter and histogram, the read-through check included, timing fields removed — against a single-threaded run, across `--threads`/`--chunk-size` combinations of (1, 7), (3, 7), (4, 13), (2, 1000) and (3, 1), with and without `--adapter-trimmed`, on input whose read-through window ends inside a chunk.

## 3. Fragment geometry and provenance: what the flags mean

A ZNA record is a stored sequence, and the question every downstream consumer asks of it is the same one: **which edges of this sequence are true fragment boundaries?** A model that learns transcript termini learns them from where fragment-end markers pile up, so a marker placed on a read-length cutoff is not a missing label — it is noise injected into the signal. The format therefore carries geometry per record rather than leaving it to be inferred.

### 3.1 The invariant

Every Illumina read begins at a fragment boundary and reads inward, so base 0 of a read as sequenced is a true fragment end. ZNA stores a record either in that frame or reverse-complemented, and records which in the `IS_RC` bit:

| `IS_RC` | true fragment boundary is at |
|---|---|
| clear | the **left** edge of the stored sequence |
| set | the **right** edge |

This holds per record with no knowledge of pairing, mate number, or strandedness, and it holds for un-normalized files too — there `IS_RC` is clear on everything and every record's left edge is its boundary, which is correct, because both mates of an untouched pair start at a fragment end.

The premise is that nothing removed *template* bases from a read's 5' end. Removing *synthetic* prefix — UMI, spacer, adapter — is not merely safe, it is required to recover the true boundary. What breaks the invariant is blind 5' clipping of template (`fastp --trim_front1`, 5'-side quality trimming). `zna merge` never does it: a merged record is built from index 0 of R1 (`s1[:take1]`, §1.8), a kept mate *is* its input, the only thing that ever shortens a read is `--npolicy trim3`, which cuts at an `N` and keeps `[0, first N)`, and the overlap consensus changes base *values*, never positions (§1.10). Measured against simulated truth: base 0 of every one of 1,416,630 records the 0.5.x benchmark emitted was a true fragment end, and 0.6 — which no longer cuts overlap from kept mates at all — shortens no kept mate anywhere except at an `N` across the 4.11M pairs of its qualification.

### 3.2 The flag byte

| bit | name | meaning |
|---|---|---|
| 0 | `IS_READ1` | record is mate 1 of a pair |
| 1 | `IS_READ2` | record is mate 2 of a pair |
| 2 | `IS_PAIRED` | record has a mate, adjacent in the file |
| 3 | `IS_RC` | strand normalization reverse-complemented this record on the way in |
| 4 | `IS_FULL_FRAGMENT` | the record spans its whole fragment: both edges are boundaries |

Bits 5–7 are reserved (`ZnaRecordFlags`, `src/zna/core.py`). Bit 4 occupies what was an unused bit, so it needs no format version bump: old readers ignore it, new readers see it clear on old files, which is the safe reading.

### 3.3 What `IS_RC` records

**`IS_RC` is a storage fact, not a mate-number fact.** It says the bases on disk were flipped relative to the bases submitted — nothing more. It cannot be recovered from the sequence, because reverse-complementing a stored record reproduces the submitted read exactly; there is no residue in the bases to test. It cannot be derived from `IS_READ1`/`IS_READ2` either: under unstranded normalization the encoder flips **one mate per pair at random**, so which mate carries the bit is a coin, not a protocol (§4.3 gives the rules). Under strand-specific normalization the bit does track the mate (and an unpaired or merged record follows the R1 rule), but a consumer that relies on that is reading a header setting through a proxy. `ENDS_BY_FLAG` (`src/zna/core.py`) is public precisely so that `blocks()` consumers, who get the raw flag column, never re-derive this.

### 3.4 `IS_FULL_FRAGMENT`

`IS_RC` names one edge and cannot say there is another. When the insert is at or below the read length — every overlap-merged read, and any pair whose mates cover the same interval — the record spans the whole fragment and both edges are real. That case is bit 4.

Who supplies it:

- **Full-overlap pairs: detected.** Two mates covering the identical interval are exact reverse complements, so `_is_reverse_complement(r1, r2)` on the submitted frames identifies them without knowing the insert size (`src/zna/cli.py`). The test probes the two end characters first, rejecting about 15/16 of ordinary pairs before the O(n) comparison runs. Measured 10051/10051 detected with 0/9949 false positives. Both mates get the bit.
- **Unpaired records: declared,** with `zna encode --treat-unpaired-as-merged`. A merged read and a genuine single-end read are byte-identical, so the encoder cannot tell them apart. Default off: an unpaired record is assumed one-ended, which under-labels rather than placing a marker at an interior position.
- **The library writer never derives it.** `ZnaWriter.write_record(is_full_fragment=…)` is always caller-supplied and says so (`src/zna/core.py`); detection lives in the `zna encode` path, which groups the stream into fragment units (`[R1, R2]` or `[single]`) and decides per unit (`_fragment_units`, `_full_fragment_flags`, `src/zna/cli.py`). The codec backends never touch bit 4.
- **Copy paths carry it** rather than re-deriving it, in both `zna encode` on a `.zna` input and `zna shuffle` (§3.5, §4.5).

What the bit does **not** guarantee is that the merger was right. It asserts that whoever produced the record believes it spans its fragment. On the hg38 benchmark, 0.5.x merged 5,591 pairs wrongly (0.96% of its merges); 0.6's plausibility gate (§1.5) refuses the divergent ones and leaves 2,627 (0.45% of 580,144 merges), of which 2,132 are emitted and 495 fall under `--min-read-length` and are dropped. On 0.5.x none was a scan failure — 0 of 848 wrong-shift merges picked a lower-scoring shift than the truth — and the survivors are the near-identical part of that population: fragments whose two ends are genuinely homologous, concentrated in pericentromeric satellite on hg38 and, on transcriptome input, in a few repeat-rich transcripts (one transcript carries 200 of 589 residual wrong merges on the clean transcriptome set; §9 of `docs/archive/MERGE_ACCURACY_PLAN.md`). A model consuming `has_start and has_end` is trusting the merger's assertion, and that assertion is wrong about once per two hundred merges on a genome that is ~50% repeat.

### 3.5 The projection: read views and copy paths

`records(with_ends=True)` yields `(seq, is_paired, is_read1, is_read2, has_start, has_end)` — six fields, or seven with a trailing `labels` on a labeled file — computed by table lookup on the flag byte:

```
has_start = is_full_fragment or not is_rc
has_end   = is_full_fragment or is_rc
```

This is the form a consumer placing fragment-end supervision wants, and it is genuinely all it wants. It is also **not invertible**:

| `IS_RC` | `IS_FULL_FRAGMENT` | byte | `(has_start, has_end)` |
|---|---|---|---|
| clear | clear | 0 | `(True, False)` |
| set | clear | 8 | `(False, True)` |
| clear | set | 16 | `(True, True)` |
| **set** | **set** | **24** | `(True, True)` |

Four reachable states, three outcomes (`_ends_from_flags` and `ENDS_BY_FLAG`, `src/zna/core.py`). Byte 24 is not a corner case — it is what the encoder writes whenever strand normalization reverse-complements a merged read, which under an unstranded coin is half of them. `ENDS_BY_FLAG` maps 16 and 24 alike to `(True, True)`, correctly, because both records do have two real ends; the cost is that no inverse function can exist. An inverse has to guess, and a guess silently clears `IS_RC` on every full-fragment record that passes through it: on a 200-record normalized file, 101 records carry `IS_RC` before a shuffle and 0 after, at which point `--restore-strand` returns half the corpus in the wrong orientation. The same loss runs through any ZNA → ZNA re-encode built on the projection.

Hence the rule the code enforces:

- **Reading** takes a view — `(is_paired, is_read1, is_read2)`, or `is_rc`, or `(has_start, has_end)`. Each is a projection chosen for a consumer, and none is complete. `restore_strand` is mutually exclusive with both `with_rc` and `with_ends`, since it *consumes* `IS_RC` to undo the flip; `with_rc` and `with_ends` are mutually exclusive with each other.
- **Copying** takes the byte. `ZnaReader.copy_records()` yields `ZnaRecord(seq, flags, labels)` — the stored byte verbatim, including combinations this version does not interpret and bits a future version may define — and `ZnaWriter.write_copy()` writes it unexamined. `ZnaRecord` is deliberately three fields wide and named, so code that confuses it with a `records()` tuple fails at the unpack instead of reading `flags` as `is_paired`. `write_records()` refuses the 6-tuples of `with_ends=True` outright (`ZnaWriter.write_records`) rather than reconstructing flags from them.
- **Producing** passes `is_full_fragment` to `write_record()`, which builds the byte.

Both copy halves require `ZnaWriter(preserve_normalization=True)`, and this is not bookkeeping: normalization is not idempotent (§4.3). Without that flag the codec would OR its own `IS_RC` into the flag column while reverse-complementing bases that already carry it, returning the file to an un-normalized state while the header still claims otherwise.

### 3.6 Where records land

| record | flags | geometry |
|---|---|---|
| merged read (`zna merge`, encoded with `--treat-unpaired-as-merged`) | unpaired; `IS_FULL_FRAGMENT`, plus `IS_RC` if normalization flipped it | `(True, True)` — the record is the fragment |
| merged read without the flag | unpaired, bit 4 clear | `(True, False)` — under-labeled, never wrong |
| unmerged mate | `IS_PAIRED` + `IS_READ1`/`IS_READ2`; exactly one mate of a normalized pair carries `IS_RC` | `(True, False)` and `(False, True)` — the two flagged edges are the two ends of the fragment |
| full-overlap pair reaching the encoder unmerged | both mates `IS_FULL_FRAGMENT`; one also `IS_RC` | `(True, True)` on both |
| genuine single-end read | unpaired, bit 4 clear | `(True, False)` |

A merged read is built from R1's 5' end outward with its mate suffix stripped (§1.8), so it arrives in R1's frame and the interleaved parser classifies it as a single. An unmerged pair is emitted all-or-nothing (§1.11), because a lone `IS_PAIRED` record would be read downstream as half a molecule. `--npolicy` never breaks a pair: `trim3` reshapes a record and `random` substitutes within it, so neither can remove one mate of two.

`zna inspect --counts` tallies the flag column without decoding sequence and prints a (mate × `IS_RC`) cross-tabulation alongside the full-fragment count. It is the cheapest way to confirm a file's geometry before training on it: a stranded file should show `IS_RC` on essentially all of one mate and none of the other, an unstranded one about 50% of each.

### 3.7 Per-record provenance: the `ZN` byte

ZNA does not store read names, so the human-readable tokens `zna merge` appends to a header (`trim3_<n>`, `subn_<n>`, `rescued_<n>`, `merged_<n1>_<n2>`) vanish at encode. The one that survives is `ZN:i:<bits>`, which `zna encode --label prov:C:ZN` turns into an ordinary `uint8` label column (§4.4); an absent tag resolves to 0 through the label's missing value, so the column is opt-in and costs a file that does not declare it nothing. The bits (`PROV_*`, `merge_core.hpp`; mirrored in `_pymerge.py`):

| bit | name | set when |
|---:|---|---|
| 1 | *retired* | was `PROV_TRIMMED`, the 0.5.x trim band's mark; never set since 0.6 |
| 2 | `PROV_RESCUED` | ≥1 no-call in the emitted bases was recovered from the mate |
| 4 | `PROV_NTRIMMED` | ≥1 base was removed by `--npolicy trim3` |
| 8 | `PROV_NSUBBED` | ≥1 base was substituted by `--npolicy random` |

**Bit 1 is retired, not reused**, so a set bit means one thing in every corpus ever written: on a 0.5.x file it still marks a trimmed pair, and no 0.6 record carries it. Nothing in the container assigns the byte a meaning — it is a label value the user declared — so retiring a bit needed no format change.

There is deliberately **no "merged" bit**: that fact already has two homes, the `merged_` token and `IS_FULL_FRAGMENT` (§3.4), and spending a bit on it would put a tag on ~80% of emitted records to say what is already said. A kept mate never carries `PROV_RESCUED`: rescue writes only into a merged record's R1 copy (§1.10), and a kept pair is emitted as read. A merged record's bits are the pair's — the N-policy counts of both mates summed. `zna encode --merge-pairs` computes the same byte in the same kernel with no FASTQ in between, and the two paths produce the same column (`test_merge_pairs_provenance_column_matches_two_step`).

### 3.8 File provenance: the prologue's merge record

Which merge policy made the records decides whether a file may enter a training corpus, and nothing in the records can answer it. So `zna encode --merge-pairs` writes a `merge` object into the file's prologue (§4.2) before the first record (`MergeParams.merge_record`, `params.py`):

```json
"merge": {"adapter_trimmed": false, "alpha": "0.000001", "error_rate": "0.01",
          "min_read_length": 40, "npolicy": "trim3",
          "policy": "zna-merge-0.6", "zna_version": "0.6.0"}
```

`alpha` and `error_rate` are decimal strings, so the exact values used survive JSON; every floor and table in §1 is reproducible from them. `policy` names the decision rule and changes whenever the decision does, so a consumer compares it for equality rather than inferring a policy from `writer_version` or `zna_version`. The record is a function of the parameters alone — nothing is read from the input — which is what lets it precede the records.

**It is carried, never re-derived.** `zna shuffle` and ZNA → ZNA re-encode copy it verbatim, exactly as they carry `merged_in_process` and `shuffled` (`test_shuffle_propagates_the_merge_record_verbatim`; the encode → shuffle → re-encode round trip in `tests/test_merge_encode.py`). **Absent means unknown**: a file from the two-step path (`zna merge` then `zna encode`) or from zna < 0.6 carries no record, and a consumer must treat that as unknown, never as a default policy. A present record that is not a JSON object is corruption, not absence (`test_a_malformed_merge_record_is_corruption_not_absence`). `zna inspect` prints it, and `zna inspect --json` splices the whole prologue.

The format version did not change for it. The record is an optional prologue key, the reader never gates on `prologue_schema`, and a missing record already means "unknown" by design; a schema bump would tell a consumer nothing the key's presence does not.

## 4. The container and the codec

### 4.1 2-bit packing

Bases are stored two bits each — `A=00`, `C=01`, `G=10`, `T=11` — four to a byte, most significant pair first. Encoding is a 256-entry ASCII→code table (case-folding: `acgt` map to the same codes as `ACGT`); decoding is a 256-entry table mapping each packed byte to its four-character string, so decode is one table lookup and one 4-byte store per input byte. Each record's sequence is padded to a whole byte — `ceil(len/4)` bytes, padding bits zero — so every record starts byte-aligned and its offset follows from the lengths column alone. Both backends zero the pad, which is why the pure-Python and compiled codecs emit byte-identical streams.

The alphabet has exactly four symbols, so **`N` cannot be stored**, and neither can `U` or any IUPAC ambiguity code. `--npolicy` decides what happens to an `N` on the way in:

| Policy | Effect |
|---|---|
| `drop` (default) | The whole **fragment** is discarded. Applied before the writer, per fragment rather than per record, so a mate is never orphaned. |
| `random` | Each `N` is replaced by a uniformly drawn base. |
| `A` / `C` / `G` / `T` | Each `N` is replaced by that base. |

The consequence is worth stating plainly: **a decoded ZNA record can never contain an `N`.** Nothing downstream needs to handle one, and nothing downstream can tell a substituted base from a called one. Two further losses follow from the same table: decode always emits uppercase, so soft-masking does not survive a round trip, and quality scores are not part of the format at all — they are consumed by the merger (§1.10) and discarded at encode.

Two implementation notes. Only `N`/`n` is substitutable, under every policy, on **both** backends — anything else raises, naming the character and its offset. (0.4.0's alphabet strictness resolved what was briefly a real divergence, where the compiled backend substituted for any unencodable character; an earlier revision of this paragraph still described that as live.) And under `random`, the compiled encoder draws in *output* order and applies the policy *after* complementing, so a reverse-complemented record packs identically whether the two steps are fused or done separately.

### 4.2 Blocks and the columnar payload

A file is a 15-byte fixed header, then variable-length read group and description, then one 89-byte definition per label, then a chain of blocks.

```
file header   magic "ZNA\x1A" | version=3 | seq_len_bytes | header flags |
              compression method | compression level | label count |
              read-group length | description length            (15 bytes, LE)
label def     name (16 B, NUL-padded UTF-8) | description (64 B) |
              dtype code (1 B ASCII) | missing value (8 B)      (89 bytes each)
block header  comp_size | uncomp_size | record_count | flags_size |
              lengths_size                                      (20 bytes, 5x uint32 LE)
block payload one zstd frame:  flags ‖ labels ‖ lengths ‖ sequences
```

Compression is zstd at `DEFAULT_ZSTD_LEVEL = 9` unless `--level` says otherwise (`src/zna/core.py`; `--level` in `src/zna/cli.py`). `seq_len_bytes` (1, 2, or 4; CLI default 2) fixes the width of the lengths column and hence the maximum record length — 255, 65535, or 4294967295 bases. A longer record raises rather than truncating.

**The file header stores no record or block count — the trailer does (0.5.0).** Since 0.5.0 the file is framed by two count-0 metadata pseudo-blocks and a footer:

```
[header] [PROLOGUE] [block 1..N] [SENTINEL + trailer JSON] [32-byte FOOTER]
```

The **prologue**, written at open, carries the facts known at encode start — `writer_version`, `shuffled`, `merged_in_process`, and the `merge` record when the merge policy is known (§3.8) — so a streaming consumer (pipes included) learns what wrote the file before decoding a record. The **trailer**, written at close, carries only facts that require the complete encode: record/base/pair counts, the length histogram overall and for unpaired records, per-flag-byte counts, the stored block index, and the prologue's crc32. The split is principled: *position in the file follows when the information is knowable.* The **footer** (magic, crc32 of the trailer payload, sentinel offset) makes discovery O(1) from EOF, so a suffix-range read of a remote file indexes it without a download. Every zstd frame carries a content checksum, and stats are tallied from the columns the codec *returned* — never the writer's inputs, which differ from the file whenever normalization sets `IS_RC` or an N-policy changes a length. The trailer is the writer's signature that the encode *finished*: an aborted encode writes none, and `zna inspect --verify` refuses the file. The format version byte stays 3 — no data block has ever had `count == 0`, so a 0.4.1 reader decodes both pseudo-blocks as valid empty blocks and terminates cleanly (the sentinel's `comp_size` deliberately covers payload *and* footer to make that true; `docs/TRAILER_PLAN.md` §14).

Every block header still carries its own count, so trailer-less files (zna < 0.5, aborted encodes) recover totals by walking the chain and seeking over each payload — measured at 2.3 µs per block, or 1.4 ms for a 38 MB / 611-block file, against 89 ms to reach the same counts by decoding. That walk is `scan_block_index()`; `block_index()` answers from the stored trailer index when one exists and falls back to the scan otherwise, and `blocks(indices=…)` then seeks past unselected blocks. Random access is therefore **block-granular** — it is per-*record* random access that the format does not provide. Blocks are flushed on an *estimated* byte size (`len/4 + 1 + seq_len_bytes` per record, default 4 MiB), so their record counts are near-uniform for fixed-length reads and vary with variable-length ones.

**A block holds whole fragments.** A fragment's reads are stored consecutively, R1 immediately followed by R2, and a fragment never straddles a block boundary. So a block is a self-contained set of molecules and any subset of blocks decodes independently of the rest of the file — which is the whole basis for `blocks(stride=…)` sharding and for block-parallel consumers: a worker handed a block never sees one mate of a pair whose other mate went to a different worker.

`ZnaWriter` enforces both halves on every write path (`OPENS_FRAGMENT` / `CLOSES_FRAGMENT`, `src/zna/core.py`). It needs no state beyond "did the last record open a fragment": that bit must equal `CLOSES_FRAGMENT[flag]` on the next record, which rejects an R1 followed by anything but its R2 *and* an R2 with no R1 in front of it, in one comparison. The size test is then asked only where a fragment ends, so the only record a block may not end on is the one whose mate has not arrived. Enforcement is what bounds the hold: a fragment is at most two records, so a block overruns its target by at most one record.

Version 2 held a weaker rule — the flush was deferred only under unstranded normalization, where the codec's pair detection requires it — and split roughly half of all block boundaries mid-fragment on every other configuration. Fixed-length reads hid it, because a constant per-record size estimate lands every boundary on an even record count. Deferring *without* enforcing was also unbounded: a run of consecutive paired R1s buffered the entire stream and wrote nothing. Version 3 files satisfy the rule by construction, and version 2 files are not readable.

The payload is columnar, not row-oriented: all flags, then all label values, then all lengths, then all packed sequence. Column order is what makes the block compress. Each stream is homogeneous, so zstd sees long runs instead of an interleave of unrelated byte types. Measured on a 25.4M-read, 150 bp library (10.76 GB FASTQ, zstd level 9, 16.5× overall): the flags stream compresses 500–1000×, the lengths stream ~1000× on uniform 150 bp reads, the label columns compress as contiguous numeric arrays, and only the sequence stream — already near-incompressible after 2-bit packing — compresses just 3–5×. Row-oriented storage would smear the three cheap columns through the expensive one.

Column order also makes partial reads possible. Flags come first, so a consumer can decompress a *prefix* of the frame and count flags without touching sequence; the shuffle's counting pass does exactly this (§4.5). Note the one hard dependency: **the block header records `flags_size` and `lengths_size` but not the label columns' width.** That is recovered as `record_count × sum(dtype sizes)` from the header schema, so a reader without the schema splits the payload at the wrong offsets — and does so silently, into plausible garbage.

### 4.3 Strand normalization

Four header bits describe the library: `STRAND_SPECIFIC`, `READ1_ANTISENSE`, `READ2_ANTISENSE`, `STRAND_NORMALIZED`. From them the writer derives three encode-time rules:

- `rc_r1 = normalized and specific and read1_antisense`
- `rc_r2 = normalized and specific and read2_antisense`
- `random = normalized and not specific`

**Stranded.** Each record is reverse-complemented iff its mate number matches an antisense rule. A record that is neither R1 nor R2 — a single-end or overlap-merged read — takes the R1 rule (`encode_core`, `src/zna/_accel.cpp`), because a merged read is R1 followed by the reverse complement of R2's tail and is therefore R1-oriented.

**Unstranded.** There is no sense strand to normalize to, so the rule is symmetry instead. An FR pair covers the two ends of one fragment pointing inward, so as sequenced the mates sit in opposite frames. For each paired R1, one fair coin decides which of the two mates to reverse-complement; **exactly one always is**, which puts both into a single common frame. Unpaired records get an independent coin.

The codec finds a fragment's two mates by looking at adjacent records within one block, which it may do because §4.2 guarantees they are there. It raises rather than guessing if they are not, so a caller reaching the backend directly gets an error instead of a half-normalized fragment.

The resulting geometry is the reason `IS_RC` is stored per record rather than inferred: in the common frame the reverse-complemented mate has its **right** edge on the real fragment boundary and its left edge at a read-length cutoff, and the other mate is the mirror image. §3.3 gives the semantics and §3.5 the read/copy rule that follows from them.

**Normalization is not idempotent.** Applying it a second time returns the data to an un-normalized state while the header still reports `strand_normalized`. Every ZNA→ZNA path therefore *copies* orientation rather than re-deriving it: the writer's `preserve_normalization=True` disables all three rules, and `copy_records()` → `write_copy()` carries the flag byte verbatim, including bits this version does not interpret.

### 4.4 Labels

A label is a fixed-width numeric column, one value per record, defined once in the file header. Types are the SAM/BAM auxiliary type codes `A c C s S i I f`, plus three 8-byte ZNA extensions `d` (float64), `q` (int64), `Q` (uint64). Each definition stores a name (≤16 UTF-8 bytes), a description (≤64 bytes), the dtype code, and a missing-value sentinel packed in the dtype's native little-endian form and zero-padded to 8 bytes. The sentinel defaults to zero for every dtype.

Values are extracted from the FASTQ header by a SAM-tag rule:

1. Split the raw header on **any** whitespace. Splitting on space alone is not enough — tools such as fastp append bare space-separated tokens like `merged_150_87`, which would otherwise be glued onto the last tag's value.
2. **Skip token 0**: it is the read name.
3. Match each remaining token as `KEY:TYPE:VALUE`. `KEY` is everything before the first colon and must be non-empty; the byte after it must be followed by another colon. Keys may be any length, so both two-character SAM tags and long custom keys work. `TYPE` is parsed for position and then **ignored** — the schema's dtype governs conversion, not the header.
4. Convert by dtype: `A` takes the single byte's ordinal, `f`/`d` go through `float()`, everything else through `int()`. The compiled fast path handles only a short run of ASCII digits and hands everything else to CPython, so both the value and the exception are the reference implementation's by construction.
5. Any tag absent from the header gets that label's missing value.

Matching uses the label's `tag` when one is defined, otherwise its `name` — which lets a file parse `AS` from the input and store the column as `aln_score`. `tag` is an encode-time field only and is **not** written to the file, so a decoded file reports names.

On disk the columns sit between the flags and the lengths, in header order, each a contiguous run of `record_count` fixed-width values. A reader can therefore skip them (`blocks(labels=False)`), receive them columnar (`labels=True`), or get them per record — but never by accident: `blocks()` on a labeled file raises unless the caller says which. Skipping does not avoid inflating the bytes, since the block is one zstd frame; it avoids unpacking them into Python objects, which is where the cost is (about 1.9× on a three-column file).

### 4.5 The shuffle

Training data wants arbitrary record order, and `blocks()` sharding hands each worker contiguous runs, so any grouping in the input becomes a biased sample. `zna shuffle` is a two-pass bucket shuffle with bounded memory.

The unit of shuffling is a **fragment**, not a record: an unpaired record, or a paired R1 together with the R2 that follows it. Pairs must stay adjacent and in order, so a pair may never be split across buckets — otherwise the mates end up arbitrarily far apart in the output and the pairing is unrecoverable. A unit start is any flag byte with `(f & 0x05) != 0x04`, i.e. anything that is not a paired non-R1.

**Pass 0 — count.** Walk the block chain. For each block, decompress only the first `flags_size` bytes of the frame (a zstd frame reads as a prefix) and translate the flag column through a 256-entry table to count unit starts; record counts come free from the block headers. No base is decoded.

**Pass 1 — distribute.** `K` is chosen so a loaded bucket is about `buffer_bytes`: `bytes_per_unit = max(file_size / n_units, 64)`, `K = ceil(n_units / (buffer_bytes / bytes_per_unit))`, clamped to `min(n_units, 4096)`. Each unit is assigned to a uniformly random bucket; an R1 pins the bucket so its R2 lands in the same one. Buckets are ZNA files written at zstd level 1 — they are read exactly once and deleted, so spending the source file's compression level on them buys a ratio nothing benefits from. The output file keeps the user's level.

**Pass 2 — collect.** Bucket order is itself shuffled. Each bucket is read whole into memory, its units Fisher-Yates shuffled, and appended to the output. Uniform independent assignment, a uniform permutation within each bucket, and a uniform bucket order compose to a uniform permutation over all units.

Every writer in both passes runs `preserve_normalization=True` and copies each record's flag byte verbatim. A shuffle is a pure permutation, so orientation must be carried, not re-derived (§4.3): re-deriving would reverse-complement once on the bucket pass and again on the output pass, leaving sequences that still look plausible but whose `IS_RC` no longer corresponds to the real fragment boundary — and the same applies to `IS_FULL_FRAGMENT`, which no projection can reconstruct (§3.5).

What survives a shuffle: every record's full flag byte, its label values, R1-before-R2 adjacency within each pair, and the file header — read group, description, `seq_len_bytes`, strand flags, compression settings, and label schema. Given the same seed, input, and buffer size, the output is byte-reproducible. What does not survive is block boundaries; records are re-blocked at the output writer's block size.
